# dsh-ui-tweaks — масштаб интерфейса Harness с клавиатуры

Твики интерфейса DeepSeek Harness. Первый твик — масштаб: по нажатию клавиш меняется
размер **всего интерфейса** (текст, отступы, колонки), а не только текст переписки.
Дальше в этот же плагин планируется твикер с галочками «включить/выключить» для каждого
твика.

Пакет для локальной установки называется `@local/dsh-ui-zoom`, репозиторий —
`dsh-ui-tweaks`: имя пакета закреплено в профиле ссылкой `link:`, и его смена
потребовала бы переустановки бандла.

## Установка

1. Скопировать папку плагина в удобное место.
2. Добавить её в `package.json` профиля (`~/.dsh/profiles/<профиль>/package.json`):

   ```json
   "dependencies": { "@local/dsh-ui-zoom": "link:<путь к папке плагина>" }
   ```

3. В `cordis.patch.yml` того же профиля включить строку плагина:
   `- id: ui-zoom` (и `disabled: false`, если строка уже есть).
4. Поставить зависимости профиля (`pnpm install` в его папке) и перезапустить приложение.

## Клавиши

| Действие | Основной блок | Нумпад | Мышь |
| --- | --- | --- | --- |
| Крупнее | `Ctrl` + `=` (и `Ctrl` + `Shift` + `=`, то есть `+`) | `Ctrl` + `+` | `Ctrl` + колесо вверх |
| Мельче | `Ctrl` + `-` (и `Ctrl` + `Shift` + `-`, то есть `_`) | `Ctrl` + `−` | `Ctrl` + колесо вниз |
| Сброс 100% | `Ctrl` + `0` | `Ctrl` + `0` (NumPad) | — |

Клавиша распознаётся и по физическому коду, и по вводимому символу: `Ctrl` + `=`
работает без Shift, а `Ctrl` + `Shift` + `=` — как знак «плюс». Раскладка при этом
не важна: смотрится позиция клавиши. Колесо меняет масштаб одним шагом за движение,
направление — как в браузере и редакторах.

Шаг — 5%, диапазон — 50…200%. Текущий размер на 1,2 с показывается плашкой в правом
нижнем углу. Значение хранится в `localStorage` устройства (ключ `dsh.ui-zoom.v1`) и
применяется при следующем открытии окна.

В Web (страница в браузере) одиночные `Ctrl` + `=` / `Ctrl` + `-` / `Ctrl` + `0` браузер
забирает себе, поэтому там те же действия доступны с `Alt`. Любую комбинацию можно
переназначить в Settings → «Горячие клавиши» (`Ctrl` + `/`): команды называются
«Увеличить размер интерфейса», «Уменьшить размер интерфейса», «Сбросить размер
интерфейса (100%)»; клавиши нумпада идут отдельными строками с пометкой «(NumPad)».

## Как устроено

* `client.js` — браузерная половина: держит значение масштаба, ставит `zoom` прямо в
  стиль корня приложения (движок без `zoom` получает `transform: scale`), регистрирует
  команды в сервисе `shortcuts` и плашку размера в слоте `shell.overlay`. Плюс прямой
  перехват клавиш: часть сочетаний сервис горячих клавиш команде не отдаёт.
* `index.js` — хост-половина: пустая, вся работа клиентская.
* `cordis.patch.yml` — вставка строки плагина в профиль.

### Носитель масштаба — корень приложения

Масштаб сделан через CSS `zoom`: он меняет и текст, и геометрию разом и остаётся
согласованным с попаданием курсора, в отличие от `transform: scale`. Носитель — корень
приложения (`#root`).

Размеры носителя при этом **не трогаются**: движок сам отдаёт содержимому логическую
ширину `ширина / масштаб`, поэтому интерфейс заполняет окно. Проверено в живом
приложении: с компенсацией размеров (`width: calc(100% / k)`) интерфейс при 125%
сжимался до 80% окна и прижимался к левому верхнему углу, а при 90% растягивался до 111%
и уходил за края. Масштаб на `body` по той же причине ломает вёрстку — размеры `body`
распределяет само приложение.

### Попапы: координаты хранятся, деление делает CSS

Меню, подсказки и диалоги приложение монтирует порталами прямо в `body` мимо корня,
поэтому общий зум-контекст их не задевает: масштаб ставится каждому слою свой.
Координаты таких слоёв приложение считает вьюпортными пикселями: `left`/`top` берутся
из `getBoundingClientRect` якоря, а `offsetWidth`/`offsetHeight` — для выравнивания по
краю и подгонки под экран (`useAnchoredPosition` в `ui-primitives`). Внутри зум-контекста
слоя CSS-пиксели умножаются на масштаб — значит, длину нужно поделить.

Делит её **сам браузер**. Плагин забирает вьюпортное значение приложения в переменную,
а в свойство ставит `calc()`:

```css
/* приложение пишет --dsh-ui-zoom-src-left: 270px */
left: calc(var(--dsh-ui-zoom-src-left) / var(--dsh-ui-zoom));
```

`--dsh-ui-zoom` живёт на корне документа и наследуется слоями в `body`. Смена масштаба —
это смена одной переменной: позиции всех попапов движок пересчитывает сам, в JS не
делится ни одна координата. Отсюда и остальное:

* `offsetWidth`/`offsetHeight` отдаются приложению в вьюпортных пикселях — иначе оно
  выравнивает меню по краю кнопки и подгоняет его под экран по неверной ширине;
* при смене масштаба плагин шлёт `resize`: якорь переехал вместе с интерфейсом, и
  приложению нужно обновить координаты;
* деление в JS убрано не случайно: при нецелом масштабе частное — периодическая дробь
  (`106 / 1.05 = 100.952380…`), браузер хранит inline-длину округлённой
  (`100.952px`), и повторный пересчёт «от своего же значения» давал дрейф — меню уезжало
  в разное место экрана. При 50/100/200% деление точное, поэтому там всё работало.
  Теперь исходная координата не переписывается вовсе, и дрейфу взяться неоткуда.

Привязку попапа к кнопке средствами CSS Anchor Positioning (`anchor-name`/`position-anchor`)
плагин не использует: DSH не помечает кнопку-якорь, а позиционирует меню JS-координатами.
Пришлось бы угадывать якорь по геометрии, а при клампе у края экрана координаты перестают
соответствовать кнопке — надёжнее оказалось оставить приложению его собственную привязку
и лишь отдать деление движку.

Встроенная настройка «Font size» в Settings при этом не трогается — она отвечает только
за текст переписки.

### Меню по правой кнопке

Системное меню здесь рисует Electron: главный процесс ловит `context-menu` и вызывает
`Menu.buildFromTemplate(...).popup()` — это окно Windows, и `zoom` страницы до него не
достаёт (как `Application`/`Edit`). Плагин перехватывает правый клик, отменяет системное
меню и показывает своё: обычный слой в `body`, поэтому оно масштабируется вместе с
интерфейсом и встаёт ровно под курсором. Состав — как в системном: в поле ввода
`Undo`/`Redo`/`Cut`/`Copy`/`Paste`/`Select All`, при выделении вне поля — только `Copy`.
Команды выполняются средствами документа, вставка — через буфер обмена
(`execCommand('paste')` в Chromium недоступен).

Две вещи, на которых меню спотыкалось:

* **Прозрачный фон.** В разметке были токены `--dsw-specific-menu` и
  `--dsw-elevation-prominent` — их в теме нет, значение не подставлялось, и сквозь меню
  был виден чат. Теперь фон — существующий токен попапа `--dsw-alias-bg-overlay`, граница
  `--dsw-alias-border-l2`, подсветка наведения `--dsw-alias-bg-layer-2`. Тест следит,
  чтобы в разметку меню не попал токен, которого в теме нет.
* **Ключи вместо текста.** Подписи шли через штатный переводчик, а он отдаёт сам ключ,
  если словарь ещё не подключился (например, при перезагрузке модуля в живую страницу):
  в меню появлялось `menu.copy`. Теперь подписи берутся через `translate()`: если
  переводчик вернул ключ, текст берётся из собственного словаря плагина по активной
  локали. Тест требует, чтобы подписи были текстом, а не ключами.

### Перетаскивание полосок изменения ширины

Полоски (`AppFrame.handle` для панелей и `ConversationRoot.widthHandle` для ширины
переписки) считают сдвиг как `e.clientX - origin` и прибавляют его к ширине, которая
живёт в логических пикселях зум-контекста. Координата указателя всегда визуальная:
без поправки панель на масштабе 150% проходила бы в полтора раза больше, чем курсор, —
указатель отставал, а на 75% отставала бы панель. Плагин отдаёт этим событиям
логический `clientX` (делит на масштаб); остальные потребители координаты видят её
как раньше, потому что поправка применяется только к событиям на полоске.

### Логические размеры рамки интерфейса

Раскладку панелей считает `AppFrame`: он измеряет себя через
`getBoundingClientRect().width` и из этой ширины выводит ширины колонок. Под `zoom`
движок возвращает **визуальную** ширину (она всегда равна окну), а логическая — та,
в которой реально вёрстается сетка — в масштаб раз меньше. Без поправки колонки
считаются от неверной ширины и занимают не свою долю окна.

Плагин отдаёт рамке логические размеры — делит её `getBoundingClientRect()` на масштаб.
Ниже порога `1024` логических пикселей ширину не опускает: по нему приложение
сворачивает сайдбар (`SIDEBAR_AUTO_COLLAPSE`), и без нижней границы левая панель
исчезала при увеличении масштаба. Рамка находится по полоске (`[data-side]`), поэтому
патч ставится сразу, как только она появится; после патча плагин на полпикселя сдвигает
рамку и возвращает — иначе приложение осталось бы при раскладке, посчитанной по
визуальной ширине.

### Полоски изменения ширины ставятся по границе колонки

Свою позицию полоска получает как `left: viewport - rightbar`, и это значение под `zoom`
расходится с фактической сеткой: в живом окне при 125% полоска стояла на 1078 px, а
граница панели была на 1202 px — взяться за неё было нечем. Поэтому плагин не доверяет
этой арифметике и ставит полоску по границе самой колонки (`offsetLeft`/`offsetWidth` —
они от масштаба не зависят). Проверено в живом окне:

| масштаб | колонки (сайдбар + чат + панель) | полоска | граница панели |
| --- | --- | --- | --- |
| 100% | 323 + 1135 + 1026 = 2484 | 1454 | 1458 |
| 110% | 355 + 1000 + 1129 = 2484 | 1351 | 1355 |
| 150% | 485 + 600 + 1400 = 2484 | 1079 | 1085 |

### Известные ограничения

* Системные меню Electron (`Application` / `Edit` вверху окна) рисует сама Windows —
  до них не достаёт ни CSS, ни плагин: их размер меняется только системным масштабом.
* Чем крупнее масштаб, тем раньше DSH сворачивает левую панель: у него есть порог
  `SIDEBAR_AUTO_COLLAPSE = 1024` логических пикселей ширины рамки, а `zoom` уменьшает
  именно логическую ширину (при окне 1180 px панель сворачивается примерно с 120%).
  Это адаптивное поведение самого приложения — в браузере при том же размере окна
  происходит то же самое, просто там окно обычно шире (на 2480 px порог наступает
  около 240%). Проверено в живом окне: при масштабе 160% и окне 2484 px панель на месте.
* Вставка из буфера в своём меню идёт через Clipboard API — если приложение не выдало
  доступ к буферу, пункт «Вставить» ничего не сделает.
* Подсказки при наведении (`Tooltip`) позиционируются отдельным путём через
  `ResizeObserver` и при сильном масштабе могут центрироваться с погрешностью
  на полшага — на привязку меню к кнопкам это не влияет.
* У длинного скроллируемого меню ограничение высоты задаётся классом в `vh`
  (`Menu.module.css`), а `vh` не масштабируется зумом: при очень крупном масштабе
  длинное меню может опираться на видимую высоту окна.

## Проверка

```powershell
node --check client.js
node test\check-client.cjs
```

`test/check-client.cjs` исполняет настоящий `client.js` в песочнице с заглушками DOM:
43 проверки — шаг и границы масштаба, запись и чтение хранилища, восстановление после
испорченного значения, регистрация команд с привязками, появление команд при поздней
загрузке сервиса `shortcuts`, поведение плашки, синхронизация между вкладками,
безопасность без хранилища, ссылки только на токены темы, масштаб по `Ctrl`+колесу,
попапы (перехват координат, ширины и `max-height` в переменные с делением через
`calc()`, метрики в вьюпортных пикселях, сигнал `resize`, неизменность исходной
координаты при смене масштаба, повторный перехват без наслоения деления, полный цикл
выравнивания меню по краю кнопки, стабильность на всех масштабах 0.5…2.0), логические
размеры рамки интерфейса, логический `clientX` на полосках изменения ширины и своё меню
по правой кнопке (состав для поля ввода и для выделения).

`test/zoom-stand.html` — наглядный стенд: открыть файл в браузере, он прогоняет связку
«якорь — портал» при масштабах 0.5…2.0 (шаг 0.05, все четыре раскладки
`side` × `align`), дополнительно делая шесть смен масштаба подряд, и отдельно проверяет,
что полоска изменения ширины правой панели стоит на её границе, что при перетаскивании
панель проходит ровно столько же, сколько курсор, и что меню по правой кнопке встаёт
ровно под курсором. Печатает зазор до кнопки, выравнивание и выход за окно.

### Проверка в живом интерфейсе

Геометрию можно снять прямо из работающего приложения: `tools/zoom-report-server.py`
слушает `127.0.0.1:8111`, а временный блок диагностики в `client.js` (регион `diag-temp`)
шлёт туда отчёт — размеры `body`, корня, крупных узлов, попапов и пробников. Так были
получены замеры при 125%, 90% и 100%: при 125% корень занимал 1988×1280 из окна
2485×1600 (80% — регрессия компенсации размеров), после правки — ровно 2485×1600.

Клиентская половина в desktop-окне обновляется только при перезапуске окна: HMR для
link-пакета в desktop-режиме не перезагружает модуль. Сам приёмник и блок диагностики
удаляются после проверки — в рабочей версии их нет.

## Установка через DSH

```powershell
# из DSH: plugin_manager action=install_bundle target=<эта папка>
```

После установки профиль ссылается на эту папку, поэтому правки `client.js` подхватываются
без переустановки; достаточно перезапустить окно Harness.
